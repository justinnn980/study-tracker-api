# 01. Todo 도메인 면접 질문

`Todo.java`를 구현한 뒤 아래 질문에 답한다.

정답을 외우는 것이 아니라, 본인이 작성한 코드 기준으로 설명하는 것이 목표다.

## 필수 질문

1. `Todo` 클래스는 어떤 책임을 가지나요?

답변 방향:

- 할 일 하나의 상태를 가진다.
- 할 일을 완료 처리하는 행위를 가진다.
- 제목 검색 조건을 스스로 판단한다.

2. 왜 필드를 `private`으로 만들었나요?

답변 방향:

- 외부에서 상태를 마음대로 바꾸지 못하게 한다.
- 객체가 자신의 규칙을 지킬 수 있게 한다.
- 필요한 값만 getter로 노출한다.

3. 왜 `id`와 `title`은 `final`인가요?

답변 방향:

- 생성된 뒤 바뀌면 객체의 정체성이 흔들린다.
- 제목도 이번 미션에서는 수정 기능이 없으므로 불변으로 둔다.
- 바뀌어야 하는 값과 바뀌지 않아야 하는 값을 구분한다.

4. 왜 `completed`는 `final`이 아닌가요?

답변 방향:

- 완료 여부는 `complete()`를 통해 바뀌는 상태다.
- 객체의 상태 변경을 메서드로 표현한다.
- 필드는 바뀔 수 있지만, 아무 곳에서나 바뀌면 안 된다.

5. 왜 생성자에서 `title`을 검증하나요?

답변 방향:

- 잘못된 객체가 처음부터 만들어지지 않게 한다.
- 객체가 항상 유효한 상태를 갖게 한다.
- 사용하는 곳마다 같은 검증을 반복하지 않아도 된다.

6. `isBlank()`와 `isEmpty()`의 차이는 무엇인가요?

답변 방향:

- `isEmpty()`는 길이가 0인지 본다.
- `isBlank()`는 공백 문자만 있는지도 빈 값처럼 본다.
- 사용자 입력 검증에는 보통 `isBlank()`가 더 적합하다.

7. `matchesKeyword()`가 `Todo` 안에 있는 이유는 무엇인가요?

답변 방향:

- 제목을 기준으로 매칭되는지는 Todo가 가장 잘 안다.
- 검색 조건 판단을 외부로 흩뿌리지 않는다.
- 나중에 검색 조건이 바뀌면 Todo 내부 로직만 바꾸면 된다.

8. `matchesKeyword(null)`은 어떻게 동작해야 하나요?

답변 방향:

- 예외를 터뜨리기보다 `false`를 반환한다.
- 검색할 키워드가 없으므로 매칭되지 않은 것으로 본다.
- 다만 정책에 따라 예외를 던지는 선택도 가능하다.

9. getter는 왜 필요한가요?

답변 방향:

- 외부에서 값을 읽을 수 있게 한다.
- 필드를 직접 열지 않고 읽기 접근만 제공한다.
- 상태 변경은 getter가 아니라 명확한 메서드로 제한한다.

10. 이 클래스를 JPA Entity로 바로 써도 될까요?

답변 방향:

- 지금 형태는 순수 도메인 객체다.
- JPA Entity가 되려면 기본 생성자, 어노테이션, ID 전략 등을 고려해야 한다.
- 지금 단계에서는 JPA보다 객체 설계를 먼저 익히는 것이 목표다.

## 답변 훈련 규칙

- 각 질문에 최소 2문장으로 답한다.
- "그냥", "몰라서", "강의에서 봐서"로 답하지 않는다.
- 본인 코드의 필드명과 메서드명을 반드시 언급한다.
- 모르는 질문은 외우지 말고 코드로 다시 돌아간다.
